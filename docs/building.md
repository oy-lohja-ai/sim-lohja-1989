# Building SIM LOHJA 1989

```sh
tools/fetch-third-party.sh   # once: Krill's loader, Blackbird's Birdcruncher and the music player, fonts
make                         # build/simlohja-a.d64, build/simlohja-b.d64 (about a minute)
make check                   # SHA-256 against the released competition images (rc10.sha256)
make run                     # VICE: side A, Alt+N flips to side B
```

Every `make` is a full build: the integration step rebuilds every part from scratch, so there is no stale state to
worry about. Outputs:

| File | Contents |
| --- | --- |
| `build/simlohja-a.d64`, `build/simlohja-b.d64` | the two disk sides |
| `build/simlohja.labels` | VICE monitor labels of the resident code and scene tables |
| `build/integraatio/kokoa.txt` | integration report: scenes, sides, blocks, preloads |
| `build/part-<part>.d64` | each scene as its own part disk (by-product, see below) |

## Third-party parts

None of these are in the repository. `tools/fetch-third-party.sh` downloads them into `third_party/downloads/`,
checks their SHA-256, builds what needs building and checks the results against the release build. To do it by hand,
follow the script: it is short, and every file it produces has its expected SHA-256 next to it.

| Part | Source | Built with | Result |
| --- | --- | --- | --- |
| Krill's Loader, repository version 194 | `https://csdb.dk/getinternalfile.php/238373/loader-v194.zip` ([CSDb release 226124](https://csdb.dk/release/?id=226124)) | `tools/krill/koosta.py`: unpacks the zip into a temporary directory and runs ca65/ld65 with the same arguments as the loader's own Makefile (`PLATFORM=c64 INSTALL=1000 RESIDENT=01fc ZP=e0`), with two small source patches: watchdog off and no "Buggy 1541U firmware" warning screen | `tools/krill/install-c64.prg`, `loader-c64.prg`, `krill.inc` |

## How the build works

`make` runs `tools/disk/kokoa.py`, the integration that assembles the whole demo:

1. The parts and their order come from `src/runko/jarjestys.json`. Each part is built as its own part disk
   (`make part P=<part>`, rules in `src/runko/runko.mk`), whose description `src/runko/part-<part>.json` lists the
   part's files and the command that builds them (usually `make -C src/proto/<scene> demo`). The scene table
   `src/scene/<part>_glue.asm` (or one generated by the scene's build) tells when each file is loaded and when the
   scene starts, waits and hands over to the next one.
2. The disk flip screens, the transitions between scenes, the MS-DOS intro and the end credits are built from
   `src/runko/`.
3. kokoa.py chains the scene tables, plans which files of the next scene are preloaded during the previous one,
   splits the scenes over the two disk sides (the flip comes after the Hillner scene), packs the resident code with
   ZX0 into the boot file and writes the D64 images with Krill's sector interleave (`tools/disk/levy.py`,
   `tools/disk/d64.py`).

### Why the disk layout is reproducible

The preload plan and some timing depend on measurements from VICE runs of the whole demo: which memory pages each
scene leaves untouched (`muisti.json`), when loads finished and scenes started (`mittaus.json`), and the song
position at which the sprite record scene starts its own SID stream (`kohdat.json`). `timing/integraatio/` holds the
exact state measured for the competition build, and kokoa.py copies it into an empty `build/integraatio/` on every run, so the
build always produces the released disks.

If you change a scene, the old measurements may no longer fit: kokoa.py still builds, but a preloaded file could land
in memory the changed scene now uses. Check such builds by running them.

### Other committed build inputs

- `src/gen/timing.inc`: scene timing symbols; `timing/timeline.c64.json` holds the same timeline in JSON form. Change
  both together.
- `timing/beatgrid.json`: the song's beat grid, used by the drawing library.
- `music/`: Patemathic's songs in Blackbird 1.2 format, named in `tools/music/song.json`. `music.py build` relocates
  the player to the address each part needs. `music/<song>.mut.json` lists the player bytes that change while the
  song plays; the disk flip loop saves and restores them. It was measured with `python3 -I tools/music/music.py mut`
  (runs `src/music/mut.asm` in x64sc).
- `tools/gfx/data/`: the demo's graphics in C64 form (bitmaps, character sets, sprites, Koala pictures and arrays of
  C64 palette indices). Some pictures started from a local image model and were converted and fixed by the agents;
  others were drawn as pixels or in code. The scene generators (`src/proto/<scene>/build.py`, `tools/gfx/`) turn this
  data into 6510 tables.
- `tools/gfx/data/ryhmalogot/`: C64-resolution renderings of the greeted groups' logos, as they appear on the
  released disks: the pit signs (`kyltit_roolit.npz`, used by `src/proto/kuoppa/kyltit.py`), the sprite record
  (`spritet/`), the transition into Sokeripala (`tahtivali/`) and the supporter logo in the end credits
  (`tukijat.npz`, `tools/disk/loppu.py`). The original logo artwork is not included.

## Single scenes

After one `make`, a single scene can be built as its own disk, which plays that scene with its music:

```sh
make part P=hillner           # build/part-hillner.d64
x64sc -autostart build/part-hillner.d64
```

The part names are the entries of `src/runko/jarjestys.json` (with `spritet-lentavat` for `spritet`).
